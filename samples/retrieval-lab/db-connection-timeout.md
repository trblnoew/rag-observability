# DB Connection Timeout 대응 Runbook

## 문서 목적

이 문서는 트래픽이 증가한 뒤 애플리케이션에서 `connection timeout`이 발생할 때 원인을 좁히고 안전하게 복구하기 위한 운영 절차다. 여기서 timeout은 SQL 실행 시간이 길다는 뜻과 같지 않다. 애플리케이션이 HikariCP 풀에서 정해진 시간 안에 사용할 수 있는 DB 연결을 빌리지 못했다는 뜻일 수 있으므로, 먼저 연결 획득 단계와 SQL 실행 단계를 분리해서 본다. 장애 대응자는 에러 한 줄만 보고 풀 크기를 바로 늘리지 말고 애플리케이션 풀, PostgreSQL 연결 제한, 장기 트랜잭션을 같은 시간축에서 확인해야 한다.

## 최초 5분 확인

첫 번째로 HikariCP의 `active`, `idle`, `pending`, `max` 지표를 확인한다. `active`가 `max`에 붙어 있고 `pending`이 계속 증가하며 `idle`이 0이라면, 모든 연결이 사용 중이어서 새 요청이 기다리는 풀 고갈 가능성이 높다. 반대로 풀에 `idle` 연결이 남아 있는데도 timeout이 난다면 네트워크 단절, 인증 실패, DNS 문제 또는 DB 측 신규 연결 거부를 의심한다. 한 인스턴스만 보지 말고 동일 버전으로 실행 중인 모든 애플리케이션 인스턴스의 풀 지표를 합산해야 한다.

같은 시각의 요청량, 오류율, p95 응답 시간과 배포 이벤트도 함께 본다. 갑작스러운 트래픽 증가 없이 배포 직후 문제가 시작됐다면 커넥션을 닫지 않는 코드, 트랜잭션 범위 확대, 새로 추가한 느린 쿼리를 우선 의심한다. 트래픽과 함께 선형으로 증가했다면 현재 동시성에 비해 풀이 작거나 DB 처리량이 부족할 수 있다. 그러나 풀 크기 확대는 DB가 수용할 수 있는 총 연결 수를 계산한 뒤에만 수행한다.

## PostgreSQL 연결 여유 계산

PostgreSQL의 `max_connections`에서 운영자 접속, 마이그레이션, 모니터링과 관리 작업용 여유분을 제외한 값이 애플리케이션 전체가 사용할 수 있는 상한이다. 예를 들어 DB가 200개 연결을 허용하고 30개를 관리용으로 남긴다면 애플리케이션 예산은 170개다. 애플리케이션 인스턴스가 10개이고 각 HikariCP `maximumPoolSize`가 20이면 이론상 200개를 요구하므로 이미 예산을 넘는다. 오토스케일링으로 인스턴스가 늘어날 때도 `인스턴스 수 × 인스턴스별 max pool` 계산을 다시 해야 한다.

`pg_stat_activity`에서 현재 연결 수를 상태별로 집계하고 `active`, `idle`, `idle in transaction`을 구분한다. `idle in transaction`이 오래 유지되는 세션은 트랜잭션을 시작한 뒤 커밋이나 롤백을 하지 않은 요청일 수 있다. 이런 장기 트랜잭션은 연결 하나를 계속 점유할 뿐 아니라 vacuum 진행과 row version 정리를 방해할 수 있다. 단순히 세션을 종료하기 전에 어떤 애플리케이션, 사용자, 쿼리와 요청에서 만들어졌는지 식별하고 영향 범위를 기록한다.

## 장기 실행 쿼리와 누수 조사

연결이 모두 `active`라면 각 세션의 `query_start`, `state_change`, `wait_event_type`, `wait_event`를 확인한다. CPU를 사용하며 오래 실행되는 쿼리와 lock을 기다리며 멈춘 쿼리는 해결 방식이 다르다. lock 대기라면 blocking session과 blocked session 관계를 찾아 선행 트랜잭션이 왜 끝나지 않았는지 조사한다. 실행 계획 악화라면 최근 통계 변경, 인덱스 사용 여부, 반환 행 수 증가를 확인하되 장애 중 무리한 인덱스 생성은 피한다.

애플리케이션에서는 모든 JDBC 사용 경로가 try-with-resources 또는 Spring 트랜잭션 경계 안에서 정상 반환되는지 확인한다. 외부 HTTP 호출을 DB 트랜잭션 안에서 기다리는 코드는 외부 서비스 지연만큼 연결을 점유하므로 특히 위험하다. 파일 처리, 대규모 반복문, 사용자 입력 대기 역시 트랜잭션 밖으로 분리한다. HikariCP leak detection 로그는 의심 경로를 찾는 보조 자료이며, 너무 낮은 임계값은 정상 장기 요청도 누수처럼 보이게 하므로 실제 SLA보다 충분히 크게 설정한다.

## 안전한 완화 순서

우선 신규 부하를 줄이기 위해 과도한 재시도와 동시 요청을 제한한다. timeout을 만난 모든 요청이 즉시 재시도하면 이미 가득 찬 풀에 더 많은 대기자를 만들어 장애를 증폭시킨다. 재시도가 필요하다면 제한된 횟수, 지수 backoff와 jitter를 적용하고 멱등성이 보장된 작업에만 사용한다. 읽기 트래픽을 줄일 수 있는 기능 플래그나 임시 rate limit이 있다면 사용자 영향과 함께 검토한다.

명확한 blocking transaction이 있고 종료 영향이 확인됐을 때만 해당 세션 취소 또는 종료를 선택한다. 풀 크기를 임시로 늘릴 때는 DB 연결 예산과 CPU, 메모리 여유를 동시에 확인한다. DB가 이미 CPU 포화 상태라면 연결 수를 늘리는 조치는 대기 쿼리만 늘려 전체 지연을 악화시킬 수 있다. 장애 완화 뒤에는 임시 설정을 영구값으로 남기지 말고 원래 값과 변경 시각을 기록한다.

## 복구 확인과 사후 조치

복구 판단은 단순히 오류가 사라진 순간이 아니라 HikariCP `pending`이 0 근처로 내려가고 `idle` 연결이 회복되며 p95 지연이 정상 범위로 돌아온 상태로 한다. PostgreSQL의 총 연결 수가 운영 예산 아래인지, 장기 트랜잭션과 lock 대기가 제거됐는지도 확인한다. 최소 15분 동안 재발하지 않는지 관찰하고 트래픽 변화가 없었는지 함께 기록한다.

사후 분석에는 장애 시작과 종료 시각, 최초 증상, HikariCP active/max 비율, PostgreSQL 연결 수, 가장 오래된 트랜잭션, 배포 여부와 완화 조치를 포함한다. 재발 방지를 위해 풀 대기자 수, connection acquisition latency, `idle in transaction` 지속 시간에 경보를 둔다. 용량 계획에는 최대 인스턴스 수를 사용해 전체 풀 상한을 계산하고, DB 관리 연결을 위한 여유분을 명시한다. 최종적으로 연결 timeout은 풀 설정 하나의 문제가 아니라 요청 동시성, 트랜잭션 수명, 쿼리 처리량과 DB 연결 예산이 만나는 지점의 문제로 다룬다.
